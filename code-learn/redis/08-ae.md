## 0. 概述

Redis 常被描述为"单线程但高性能"。这个"单线程"就是指 **AE（A simple Event-driven library）事件循环**——452 行 C 代码（`ae.c` + `ae.h`），支撑了整个 Redis 的 I/O 多路复用、定时器调度、以及命令处理。

核心流程：

```
aeMain()                    ← 事件主循环
└── aeProcessEvents()       ← 单次事件处理
    ├── beforesleep()       ← server.c:1652，睡眠前的全局钩子
    ├── aeApiPoll(tvp)      ← 多路复用等待（epoll_wait / kqueue/select）
    ├── aftersleep()        ← 唤醒后的全局钩子
    └── 遍历 fired[] 事件
        ├── 可读事件 → fe->rfileProc(fd)
        └── 可写事件 → fe->wfileProc(fd)
    └── processTimeEvents() ← 定时器事件处理
```

**doom-lsp 确认**：核心文件

| 文件 | 行数 | 职责 |
|------|:----:|------|
| `src/ae.h` | 136 | 结构定义 + API |
| `src/ae.c` | 512 | 事件循环核心 |
| `src/ae_epoll.c` | 139 | Linux epoll 后端 |
| `src/ae_evport.c` | — | Solaris event ports 后端 |
| `src/ae_kqueue.c` | — | macOS/FreeBSD kqueue 后端 |
| `src/ae_select.c` | — | POSIX select 后备 |
| `src/server.c` | ~7264 | beforeSleep/afterSleep 实现 |

## 2. 事件循环结构

### 2.1 aeEventLoop——全局状态

```c
// ae.h:99-112 — doom-lsp 确认
typedef struct aeEventLoop {
    int maxfd;                      // 当前注册的最大 fd
    int setsize;                    // 数组容量（最大 fd + 1）
    long long timeEventNextId;      // 定时器 ID 生成器
    aeFileEvent *events;            // 文件事件数组（index = fd）
    aeFiredEvent *fired;            // 就绪事件数组
    aeTimeEvent *timeEventHead;     // 定时器链表头
    int stop;                       // 停止标志
    void *apidata;                  // 多路复用后端私有数据
    aeBeforeSleepProc *beforesleep; // 阻塞前回调
    aeBeforeSleepProc *aftersleep;  // 阻塞后回调
    int flags;
} aeEventLoop;
```

**关键设计决策**：**文件事件用数组，定时器用链表**。

- `events` 数组按 **fd 索引**（`events[fd]`），O(1) 定位任一文件描述符的事件状态
- `timeEventHead` 是**无序单向链表**，插入 O(1)，但查找最早定时器需要 O(N) 遍历

这个取舍来自 Redis 的现实：成千上万个 client fd 需要 O(1) 的事件管理，但定时器数量很少（通常只有 serverCron 等几个），O(N) 遍历无伤大雅。

## 3. 文件事件

### 3.1 aeFileEvent——按 fd 索引的事件注册

```c
// ae.h:72-78 — doom-lsp 确认
typedef struct aeFileEvent {
    int mask;               // AE_READABLE | AE_WRITABLE | AE_BARRIER
    aeFileProc *rfileProc;  // 可读时调用
    aeFileProc *wfileProc;  // 可写时调用
    void *clientData;       // 透传上下文（通常是 client 指针）
} aeFileEvent;
```

**注册**：

```c
// ae.c:157-174 — doom-lsp 确认
int aeCreateFileEvent(aeEventLoop *eventLoop, int fd, int mask,
        aeFileProc *proc, void *clientData)
{
    if (fd >= eventLoop->setsize) return AE_ERR;
    aeFileEvent *fe = &eventLoop->events[fd];

    if (aeApiAddEvent(eventLoop, fd, mask) == -1)
        return AE_ERR;              // 通知 epoll 添加监听
    fe->mask |= mask;
    if (mask & AE_READABLE) fe->rfileProc = proc;
    if (mask & AE_WRITABLE) fe->wfileProc = proc;
    fe->clientData = clientData;
    if (fd > eventLoop->maxfd)
        eventLoop->maxfd = fd;
    return AE_OK;
}
```

**删除**：

```c
// ae.c:176-198 — doom-lsp 确认
void aeDeleteFileEvent(aeEventLoop *eventLoop, int fd, int mask)
{
    if (fd >= eventLoop->setsize) return;
    aeFileEvent *fe = &eventLoop->events[fd];
    if (fe->mask == AE_NONE) return;

    if (mask & AE_WRITABLE) mask |= AE_BARRIER;
    aeApiDelEvent(eventLoop, fd, mask);   // 通知 epoll 删除监听
    fe->mask = fe->mask & (~mask);

    // 如果删除的是最大 fd，更新 maxfd
    if (fd == eventLoop->maxfd && fe->mask == AE_NONE) {
        for (j = eventLoop->maxfd-1; j >= 0; j--)
            if (eventLoop->events[j].mask != AE_NONE) break;
        eventLoop->maxfd = j;
    }
}
```

**Redis 中的典型注册场景**（`server.c:2404`）：

```c
// server.c:2404 — doom-lsp 确认
// 监听 TCP 端口：accept_handler 负责 accept 新连接

// server.c:2736 — doom-lsp 确认
// 监听 UNIX socket
aeCreateFileEvent(server.el, server.sofd, AE_READABLE, ...);
```

### 3.2 AE_BARRIER——写屏障

`AE_BARRIER` 是可写事件的一个修饰符：**如果在本次事件循环中可读事件已经触发，则不触发可写事件**。

```c
// ae.c:413-452 — aeProcessEvents 中的处理
int invert = fe->mask & AE_BARRIER;

// 无 BARRIER：先读后写（默认行为）
if (!invert && fe->mask & mask & AE_READABLE) {
    fe->rfileProc(...);    // 处理查询 → 生成响应
    fired++;
}
if (fe->mask & mask & AE_WRITABLE) {
    fe->wfileProc(...);    // 写回响应
}

// 有 BARRIER：写优先，然后读
if (invert) { /* 先写后读 */ }
```

**用途**：当 `beforeSleep` 中需要先 fsync AOF 文件再回复客户端（保证数据落盘后才发送"OK"），设置 AE_BARRIER 确保**可写事件在可读事件之前处理**。

### 4.2 aeApiCreate——创建 epoll 实例

```c
    aeApiState *state = zmalloc(sizeof(aeApiState));
    state->events = zmalloc(sizeof(struct epoll_event) * eventLoop->setsize);

```

`epoll_create(1024)` 的 1024 在 2.6.8+ 之后被内核忽略，这里仅作为可读的文档性数字。

### 4.3 aeApiAddEvent——添加/修改监视

```c
// ae_epoll.c:70-83 — doom-lsp 确认
static int aeApiAddEvent(aeEventLoop *eventLoop, int fd, int mask) {
    aeApiState *state = eventLoop->apidata;
    struct epoll_event ee = {0};
    int op = eventLoop->events[fd].mask == AE_NONE ?
             EPOLL_CTL_ADD : EPOLL_CTL_MOD;

    mask |= eventLoop->events[fd].mask;  // 合并已有事件
    ee.events = 0;
    if (mask & AE_READABLE) ee.events |= EPOLLIN;
    if (mask & AE_WRITABLE) ee.events |= EPOLLOUT;
    ee.data.fd = fd;
    epoll_ctl(state->epfd, op, fd, &ee);
}
```

**合并已有 mask**：`mask |= eventLoop->events[fd].mask`。因为 `aeCreateFileEvent` 调用时只传入新增的事件掩码（如只传入 `AE_READABLE`），要与之前已经注册的 `AE_WRITABLE` 合并后才写入 epoll。

**EPOLL_CTL_ADD vs EPOLL_CTL_MOD**：根据 events 表判断——如果该 fd 当前没有任何事件，用 ADD；已有事件，用 MOD。避免 `EEXIST` 错误。

### 4.4 aeApiPoll——等待事件

```c
// ae_epoll.c:99-118 — doom-lsp 确认
static int aeApiPoll(aeEventLoop *eventLoop, struct timeval *tvp) {
    aeApiState *state = eventLoop->apidata;

    retval = epoll_wait(state->epfd, state->events, eventLoop->setsize,
             tvp ? (tvp->tv_sec*1000 + (tvp->tv_usec + 999)/1000) : -1);

    if (retval > 0) {
        for (j = 0; j < retval; j++) {
            int mask = 0;
            if (e->events & EPOLLIN)  mask |= AE_READABLE;
            if (e->events & EPOLLOUT) mask |= AE_WRITABLE;
            if (e->events & EPOLLERR) mask |= AE_WRITABLE|AE_READABLE;
            if (e->events & EPOLLHUP) mask |= AE_WRITABLE|AE_READABLE;
            eventLoop->fired[j].fd = e->data.fd;
            eventLoop->fired[j].mask = mask;
        }
    }
    return numevents;
}
```

epoll 的超时由 `aeProcessEvents` 根据最近定时器计算得出（见 5.4 节）。`epoll_wait` 返回后，将就绪事件的 fd 和 mask 写入 `fired[]` 数组，供上层遍历处理。

## 5. 事件调度——aeProcessEvents

### 5.1 完整流程

```c
// ae.c:364 — doom-lsp 确认
int aeProcessEvents(aeEventLoop *eventLoop, int flags)
{
    // 1. 计算最近的定时器距当前的时间差（微秒）
    usUntilTimer = usUntilEarliestTimer(eventLoop);

    // 2. 设置 epoll_wait 超时
    if (usUntilTimer >= 0) {
        tvp->tv_sec = usUntilTimer / 1000000;
        tvp->tv_usec = usUntilTimer % 1000000;
    } else if (flags & AE_DONT_WAIT) {
        tv.tv_sec = tv.tv_usec = 0;  // 不等待
    } else {
        tvp = NULL;                   // 无限等待
    }

    // 3. beforesleep 回调（server.c 的前置处理）
    if (eventLoop->beforesleep && flags & AE_CALL_BEFORE_SLEEP)
        eventLoop->beforesleep(eventLoop);

    // 4. 多路复用等待（核心阻塞点）
    numevents = aeApiPoll(eventLoop, tvp);

    // 5. aftersleep 回调
    if (eventLoop->aftersleep && flags & AE_CALL_AFTER_SLEEP)
        eventLoop->aftersleep(eventLoop);

    // 6. 遍历就绪事件
    for (j = 0; j < numevents; j++) {
        int invert = fe->mask & AE_BARRIER;

        // 先读后写（默认）
        if (!invert && fe->mask & mask & AE_READABLE)
            fe->rfileProc(...);
        if (fe->mask & mask & AE_WRITABLE)
            fe->wfileProc(...);
        // BARRIER：先写后读
        if (invert) { /* reversed order */ }
    }

    // 7. 处理定时器
    if (flags & AE_TIME_EVENTS)
        processed += processTimeEvents(eventLoop);

    return processed;
}
```

### 5.2 beforesleep——睡眠前的全局钩子

```c
// server.c:1652-1737 — doom-lsp 确认
void beforeSleep(struct aeEventLoop *eventLoop) {
    // 1. 更新内存峰值统计
    if (zmalloc_used > server.stat_peak_memory)
        server.stat_peak_memory = zmalloc_used;

    // 2. 处理 pending 读（I/O 线程）
    handleClientsWithPendingReadsUsingThreads();

    // 3. 处理 TLS 待定数据
    tlsProcessPendingData();

    // 4. 如果 AOF 开启，flush AOF 缓冲区到磁盘
    if (server.aof_state == AOF_ON || ...)
        flushAppendOnlyFile(0);

    // 5. 处理 pending 写
    handleClientsWithPendingWrites();

    // 6. 快速过期检查
    if (server.active_expire_enabled && server.masterhost == NULL)
        activeExpireCycle(ACTIVE_EXPIRE_CYCLE_FAST);

    // 7. 处理 WAIT 命令的同步复制
    if (listLength(server.clients_waiting_acks))
        processClientsWaitingReplicas();

    // 8. 释放异步释放队列中的 client
    freeClientsInAsyncFreeQueue();

    // ...
}
```

**beforesleep 的设计哲学**：在事件循环开始阻塞前，把所有能做的事都做完——刷 AOF、处理 pending 写、过期删除。这样 `epoll_wait` 可以安心阻塞，不需要频繁被唤醒。

### 5.3 aftersleep——唤醒后的钩子

```c
void afterSleep(struct aeEventLoop *eventLoop) {
    // 处理模块事件
    // 处理 TLS
    // ...
}
```

`aftersleep` 在新版 Redis 中用于 `processEventsWhileBlocked` 场景——主线程在处理阻塞命令（如 `WAIT`）时仍能响应部分事件。

### 5.4 超时计算——usUntilEarliestTimer

```c
// ae.c:302-318 — doom-lsp 确认
static int64_t usUntilEarliestTimer(aeEventLoop *eventLoop) {
    aeTimeEvent *te = eventLoop->timeEventHead;
    if (te == NULL) return -1;    // 没有定时器 → 无限等待

    aeTimeEvent *earliest = NULL;
    while (te) {                  // O(N) 遍历找最早的
        if (!earliest || te->when < earliest->when)
            earliest = te;
        te = te->next;
    }

    monotime now = getMonotonicUs();
    return (now >= earliest->when) ? 0 : earliest->when - now;
}
```

注释明确指出了优化空间（`ae.c:304-309`）：

```
// 复杂度 O(N)，因为 time events 未排序。
// 可能的优化（Redis 目前不需要）：
// 1) 按序插入，最早的在头部 O(1)，但插入/删除仍是 O(N)
// 2) 用跳表实现 O(1) 查找最早、O(log N) 插入
```

Redis 的定时器极少（serverCron + 模块定时器），O(N) 遍历完全可以接受。

## 6. 定时器事件

### 6.1 aeTimeEvent——双向链表

```c
// ae.h:80-91 — doom-lsp 确认
typedef struct aeTimeEvent {
    long long id;                       // 自增 ID
    monotime when;                      // 下次触发时间（单调时钟微秒）
    aeTimeProc *timeProc;               // 触发回调
    aeEventFinalizerProc *finalizerProc; // 删除时回调
    void *clientData;
    struct aeTimeEvent *prev;           // 双向链表
    struct aeTimeEvent *next;
    int refcount;                       // 防止递归释放
} aeTimeEvent;
```

### 6.2 创建

```c
// ae.c:213-233 — doom-lsp 确认
long long aeCreateTimeEvent(aeEventLoop *eventLoop, long long milliseconds,
        aeTimeProc *proc, void *clientData,
        aeEventFinalizerProc *finalizerProc)
{
    long long id = eventLoop->timeEventNextId++;
    te = zmalloc(sizeof(*te));
    te->id = id;
    te->when = getMonotonicUs() + milliseconds * 1000;
    te->timeProc = proc;
    te->finalizerProc = finalizerProc;
    te->clientData = clientData;

    // 头插法插入链表
    te->next = eventLoop->timeEventHead;
    te->prev = NULL;
    if (te->next) te->next->prev = te;
    eventLoop->timeEventHead = te;

    te->refcount = 0;
    return id;
}
```

**插入即头插**：新定时器总是放在链表头部，不排序。`usUntilEarliestTimer` 每次遍历全链表找最早触发时间。

### 6.3 删除——惰性删除

```c
// ae.c:235-246 — doom-lsp 确认
int aeDeleteTimeEvent(aeEventLoop *eventLoop, long long id) {
    aeTimeEvent *te = eventLoop->timeEventHead;
    while (te) {
        if (te->id == id) {
            te->id = AE_DELETED_EVENT_ID;  // 标记删除，非实际释放
            return AE_OK;
        }
        te = te->next;
    }
    return AE_ERR;
}
```

**惰性删除**：只把 `id` 设为 `AE_DELETED_EVENT_ID`（-1），不实际释放。真正的释放发生在 `processTimeEvents` 中遍历时跳过这些节点。

### 6.4 processTimeEvents——定时器事件处理

```c
// ae.c:321-338 — doom-lsp 确认
static int processTimeEvents(aeEventLoop *eventLoop) {
    int processed = 0;
    te = eventLoop->timeEventHead;
    maxId = eventLoop->timeEventNextId - 1;
    now = getMonotonicUs();

    while (te) {
        // 跳过标记删除的事件
        if (te->id == AE_DELETED_EVENT_ID) {
            if (te->refcount) { te = te->next; continue; }
            // 摘除 + 释放
            if (te->prev) te->prev->next = te->next;
            else eventLoop->timeEventHead = te->next;
            if (te->next) te->next->prev = te->prev;
            if (te->finalizerProc)
                te->finalizerProc(eventLoop, te->clientData);
            zfree(te);
            te = next;
            continue;
        }

        if (now >= te->when) {      // 触发了
            te->refcount++;
            retval = te->timeProc(eventLoop, te->id, te->clientData);
            te->refcount--;

            if (retval != AE_NOMORE) {
                // 周期性定时器：重新计算下次触发时间
                te->when = now + retval * 1000;
            } else {
                // 一次性定时器：标记删除
                te->id = AE_DELETED_EVENT_ID;
            }
        }
        te = te->next;
    }
    return processed;
}
```

**周期性 vs 一次性**：`timeProc` 的返回值决定：
- 返回 `AE_NOMORE`（-1）：一次性定时器，触发后标记删除
- 返回其他值（毫秒）：周期性定时器，`when += retval * 1000`，下次间隔按返回值

## 7. aeMain——永不停止的主循环

```c
// ae.c:483-489 — doom-lsp 确认
void aeMain(aeEventLoop *eventLoop) {
    eventLoop->stop = 0;
    while (!eventLoop->stop) {
        aeProcessEvents(eventLoop, AE_ALL_EVENTS |
                                   AE_CALL_BEFORE_SLEEP |
                                   AE_CALL_AFTER_SLEEP);
    }
}
```

**这就是 Redis 的主循环**。在 `server.c:7264`：

```c
// server.c:7264 — doom-lsp 确认
aeMain(server.el);
```

进入 `aeMain` 后，Redis 进入无限循环直到进程退出。每次循环：
1. 执行 `beforesleep`：刷 AOF、处理 pending 读写、过期删除
2. 调用 `aeApiPoll`：阻塞等待 I/O 事件
3. 执行 `aftersleep`：模块事件处理
4. 遍历所有就绪的 fd，分发到对应的 `rfileProc` / `wfileProc`
5. 处理到期的定时器

**单线程的意义**：所有这一切在同一个线程中串行执行。没有锁竞争，没有上下文切换，没有并发复杂性。性能来自：
- 多路复用（一个线程管理数万连接）
- 内存操作（比磁盘/网络快几个数量级）
- 避免锁（单线程本身就是大锁）

## 8. 单线程的例外——I/O 线程

Redis 6.0+ 引入了 I/O 线程（`io-threads`），但 AE 事件循环本身仍然是单线程的。I/O 线程只在主线程**之后**分担网络读写：

```
主线程事件循环：                                I/O 线程：
beforesleep():
  handleClientsWithPendingReadsUsingThreads() → I/O 线程并行读取
  handleClientsWithPendingWrites()             I/O 线程并行写入
  ↑
  flushAppendOnlyFile()  ← 主线程执行（必须串行）
  activeExpireCycle()    ← 主线程执行
```

I/O 线程通过管道（pipe）与主线程通信。当 beforesleep 将读写任务分发给 I/O 线程后，主线程继续执行其他串行工作（AOF flush、过期删除），等 I/O 线程完成后主线程再处理命令。命令执行本身始终在单线程中。

**网络数据流**：

```
client.fd
  ↓
aeApiPoll(epoll) → fd 就绪     ← ae.c
  ↓
rfileProc = readQueryFromClient  ← networking.c
  ↓
processCommand(sds argv)         ← server.c
  ↓
dictFind(server.commands, cmd)   ← dict（第三篇）
  ↓
setCommand / getCommand / ...    ← t_string.c / t_hash.c / t_zset.c / ...
  ↓
createStringObject / ...         ← object.c（第一篇）
  ↓
sdsnewlen / ...                  ← sds.c（第二篇）
  ↓
addReply(client, reply)          ← networking.c
  ↓
beforesleep 中 flush 到 client    ← ae.c 事件循环
```

数据从 socket 到数据结构再到 socket，AE 是整个周期中的调度中枢。
